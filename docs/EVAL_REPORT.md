# Baseline vs. 低空化版本：量化对比报告

> 全部数字由 `python lowalt/eval/run_eval.py` 实测生成，逐题明细在 `lowalt/eval/results/comparison.json`，聚合指标在 `summary.json`，答案键在 `golden.lock.json`。**0 次模型调用**，重跑一致。

## 1. 实验设置与公平性

| 项 | 设置 |
|---|---|
| 数据 | 同一份 `lowalt/data/out`（27 节点 / 2 禁飞区 / 233 单 / 2097 轨迹点，5 天） |
| 题目 | 24 条：纯数据聚合 8 / 空间与时空 8 / 复合推理 8 |
| 答案键 | 每题由**独立编写的 SQL** 在原始表上计算，不读取任何工具输出（沿用上游 `evals/real` 的做法） |
| **Baseline** | **通用 SQL 工具链**：一个能写任意只读 SQL 的 `sql_aggregate`，外加空间题上的 SQL 包围盒（bbox）近似。**它从未被禁用任何一类题目，每题都能给出数值答案** |
| **低空化版** | 同一套通用工具 + 3 个注册的低空工具（口径编码进工具、多边形几何、高度层定义） |
| 自然语言入口 | 两版共用 v2 规则式 resolver（无 LLM，所求量意图 + EXACT/AMBIGUOUS/UNRESOLVED 三态），记录工具选择；执行用消歧后的 typed plan |
| 运行环境 | Python 3.13 / DuckDB 2.0.0，无模型、无网络、无随机性 |

**为什么这个 baseline 是公平的**：常见做法是拿「没有空间能力的原始工具链」去比空间题，baseline 必输，得到的「提升 X%」没有信息量。本项目反过来——baseline 直接执行独立 SQL 答案键，因此**数值正确率天然可以达到 100%**。两版的唯一差别是：数字有没有被拆成可复核事实、口径有没有被固化、几何是不是精确的、答案有没有携带维度/时间窗/口径。

## 2. 主结果

| 指标 | Baseline | 低空化版 | 差值 |
|---|---|---|---|
| 数值正确率 | **24/24 (100%)** | **24/24 (100%)** | **0.0 pp** |
| 答案完整性 (answer relevancy) | 0.399 | **0.990** | **+59.03 pp** |
| 可复核数字总数 (V2 facts) | 24 | **242** | **10.08×** |
| V2 复核通过率 | 100% | 100% | 0 |
| 平均工具步数 | 1.208 | 2.208 | +1.0 |
| 平均耗时 | 4.51 ms | 25.20 ms | +20.7 ms (5.6×) |
| 自然语言工具选择正确（两版共用 resolver） | **24/24 (EXACT)** | **24/24 (EXACT)** | v1 为 19/24，第二轮迭代后 24/24 |

> `answer relevancy` 是结构化、非 LLM 的评分：答案是否同时给出 **数值 / 所属维度 / 时间窗 / 计算口径定义 / 分组明细** 五项中的检查项，取满足比例。Baseline 的 ad-hoc SQL 只返回一个裸数字，即使数值正确也只有 0.399。

### 分层结果（这是简历里该引用的数字）

| 类别 | n | 数值正确率 B→L | 答案完整性 B→L | 可复核数字 B→L |
|---|---|---|---|---|
| 纯数据聚合 | 8 | 8/8 → 8/8 | 0.3125 → **1.0000**（**+68.75 pp**） | 8 → **132**（16.5×） |
| 空间 / 时空 | 8 | 8/8 → 8/8 | 0.5521 → **1.0000**（**+44.79 pp**） | 8 → **20**（2.5×） |
| **复合推理** | 8 | 8/8 → 8/8 | 0.3333 → **0.9688**（**+63.55 pp**） | 8 → **90**（11.25×） |
| 合计 | 24 | 24/24 → 24/24 | 0.399 → 0.990（+59.03 pp） | 24 → 242（10.08×） |

**结论要这样讲**：二次开发**没有**提升数值正确率——一个会写 SQL 的通用工具本来就能算对。它带来的是三件可量化的东西：把口径固化后答案完整性从 40% 提到 99%，把每个数字变成可被独立重算的事实（10 倍），以及在几何上消除近似误差。

## 3. 几何能力与合成探针（单独验证，不混入业务题）

**关键数据发现**：该公开基准实例的两个禁飞区与配送网络**几何零交集**——机场区经度 113.792–113.842，而全部节点与 2097 个轨迹点经度 ≥ 113.845；临时区 240 m 方形无轨迹穿过。激活窗口内虽有 1741 个轨迹点，但无一在区内。因此真实数据上冲突次数**恒为 0**，两版一致，无法用于区分几何能力。这一点被写成回归测试 `test_published_case_has_zero_geometric_intersection` 固化。

于是用 `lowalt/engine/probes.py` 中**明确标注为 synthetic** 的 3 条探针轨迹（bbox 内但多边形外 / 穿多边形 / 时间窗外）单独测算法：

| 检查 | 精确多边形（低空化版） | bbox 近似（baseline） |
|---|---|---|
| 冲突事件数 | **1** | 2（**高估 100%**） |
| 命中点数 | **9** | 18（**高估 100%**） |
| 冲突检测数值 V2 复核 | **100% 通过** | 100% 通过（但复核的是错误的几何结果） |

`lowalt/tests/` 共 8 项 golden case 全部通过：独立第二实现（角度和 winding number）与射线法在 41×41=1681 个网格点上 **100% 一致**；分段规则、时间窗过滤、未注册函数 fail-closed、零交集回归均通过。

> **重要限定**：V2 复核只证明「报告里的数字 = 存储 SQL / 输入 facts 重算的结果」。如果几何算法本身算错，物化表也跟着错，V2 照样通过。这正是为什么必须补独立第二实现 + golden cases——**验证器管一致性，golden case 管正确性**，两者不能互相替代。

## 4. 失效案例定位与第二轮迭代

数值失效 **0 例**（两版均 24/24）。v1 的失效集中在自然语言工具选择，**19/24，5 例**：

| 题号 | 期望工具 | v1 实际 | 原因 |
|---|---|---|---|
| A05 | `drone_demand_aggregate` | `sql_aggregate` | 「按小时分解…配送量」未命中需求/峰值/订单关键词 |
| S07 | `altitude_distribution` | `sql_aggregate` | 「巡航阶段轨迹点」未命中高度/层关键词 |
| C01 | `drone_demand_aggregate` | `no_fly_conflict_count` | 复合题同时提到「禁飞区」，被主题名词抢走 |
| C03 | `drone_demand_aggregate` | `no_fly_conflict_count` | 同上，「禁飞区活跃的窗口内订单」被误判为空间题 |
| C07 | `altitude_distribution` | `sql_aggregate` | 同 S07 |

**根因不是关键词不够，而是判错了对象**：v1 匹配「话题名词」，而「禁飞区活跃的窗口内共有多少配送订单」问的是**订单量**，「禁飞区」只是修饰时间窗。

### v2 修法（方法论，不是打补丁）

1. **改为识别「所求量」**：三个工具各定义一组所求量语义模式（订单/单量/峰值 → 需求；冲突次数/命中点/区内轨迹点 → 空间；高度层/巡航点 → 高度），对问题打分取最高，而不是看话题词出现与否。
2. **显式歧义态**：本地规则返回 `EXACT` / `AMBIGUOUS` / `UNRESOLVED` 三态并写入评测轨迹。两类所求量得分接近（差 ≤1）时不硬猜，返回 `AMBIGUOUS`——这正是上游「只有真正的歧义才交给 planner」的边界，且让「需要模型介入的比例」变成可测指标而非隐式假设。
3. **拒绝猜测**：无所求量时返回 `UNRESOLVED` 并落到通用 SQL，不编造工具调用。

### 验证（防止过拟合）

| 检查 | v1 | v2 |
|---|---|---|
| 24 题工具选择 | 19/24 | **24/24，全部 EXACT** |
| 8 条**独立编写的改写题**（`lowalt/tests/test_resolver_heldout.py`，措辞不来自评测集） | — | **8/8 正确** |
| 真歧义题「有多少订单和禁飞区命中点？」 | 硬猜 | **返回 AMBIGUOUS** |
| 无关题「今天天气怎么样？」 | 硬猜 | **返回 UNRESOLVED** |
| 回归：主评测集三项核心指标 | 24/24、0.399→0.990、24→242 | **完全不变** |

改写题的存在是为了证明 v2 学的是「所求量语义类别」而不是这 24 道题的词汇；主结果不变则说明这轮迭代没有动到计算层。**单测总数 8 → 12**。

## 5. Trade-off 与局限

1. **可审计性的代价是性能**：逐分组产出 fact 并逐条重跑 SQL，聚合类平均耗时 3.85 ms → 42.79 ms（约 11×），fact 数 8 → 132。数据量大时必须改成分批/增量复核。
2. **口径固化 vs 灵活性**：把「只算巡航点」「1 次冲突 = 一段连续命中」写进工具，保证了一致性，但新增口径要改代码；ad-hoc SQL 反而更灵活。
3. **几何用 Python 而非纯 SQL，偏离了「所有计算由 DuckDB 执行」的原教旨**。补偿设计：几何结果物化成 DuckDB 表，让 SQL 验证器仍能复核计数；再用独立第二实现 + golden cases 校验几何本身。
4. **V2 通过率两版都是 100%，不能当作改进指标**——它只覆盖一致性。本项目的改进在覆盖的**数字数量**（24→242）而非通过率。
5. **零模型评测 ≠ 真实 Agent 表现**：确定性回放消除了 LLM 噪声、可复现，但无法证明「有 LLM 时工具层能减少写错 SQL 的概率」。v2 在 24 题上全部 EXACT、模型介入率 0，只能说明评测集措辞规范，不能代表真实用户的模糊提问分布；歧义态目前只在单测中验证。接真实 LLM 做工具选择对照，仍是下一步该做的实验。
6. **上游 TS CLI 未在本机跑通**：`bun install` 在当前网络下持续报 `registry requests failed`（换 `--ignore-scripts` 与国内镜像均未成功），因此 TS 补丁未经 `bun run check` 编译验证；Python 链路是完整实测的。详见 `lowalt/integration/README.md`。

## 7. 补充实验：接入真实本地 LLM（无 API key、数据不出本机）

§5 曾把「零模型评测」列为局限。本节把它补上。

### 环境

| 项 | 配置 |
|---|---|
| 引擎 | llama.cpp `b12110` Windows CPU x64（24.7 MB，解压到 `E:/lowalt-llm/bin/`） |
| 模型 | Qwen2.5-1.5B-Instruct Q4_K_M GGUF（1.04 GiB，`E:/lowalt-llm/models/`） |
| 端点 | `llama-server` 仅监听 `127.0.0.1:8081`，OpenAI 兼容 `/v1/chat/completions` |
| 凭据 | **无**。不用 Groq / 不用任何云端点；数据不离开本机 |
| 确定性 | `temperature=0 / seed=42 / top_p=1`，每题 1 次 |
| 答案键 | 与主实验**同一份**独立 SQL |
| 脚本 | `lowalt/eval/run_llm_eval.py`；结果 `llm_comparison.json` / `llm_summary.json` |

> 本机 15.7 GB 内存初始仅余 1.5 GB，引擎加载失败（`CPU_REPACK buffer` 分配不到 596 MB）。关闭占用较大的前台程序后余 4.8 GB，配合 `--no-repack -c 1024` 正常加载。这是环境事实，不是模型问题。

### 五臂阶梯

| # | 臂 | 谁写 SQL | 参数约束 | 数值正确率 | 答案完整性 | 可复核数字 |
|---|---|---|---|---|---|---|
| 1 | LLM 直接写 SQL（完整口径 prompt） | 模型 | 无 | **0/24 (0%)** | 0.000 | 0 |
| 2 | LLM 直接写 SQL（**聚焦 prompt 消融**，对 SQL 臂更有利） | 模型 | 无 | **4/24 (16.7%)** | 0.000 | 0 |
| 3 | LLM 选工具 + 仅类型校验（上一轮快照 `llm_*_typed_only.json`） | 工具 | 类型/范围 | **7/24 (29.2%)** | 0.750 | — |
| 4 | **LLM 选工具 + 类型 & 问题约束校验** | 工具 | 类型 + 问句约束 | **22/24 (91.7%)** | **0.955** | **215** |
| 5 | 规则式 resolver + 工具层（§2 主实验，无 LLM） | 工具 | 结构化 plan | **24/24 (100%)** | 0.990 | 242 |

第 4 臂分层：聚合 **8/8**、空间 **8/8**、复合 **6/8**；工具选择 22/24；平均 4.33 s/题。

### 每一级差值是怎么来的（消融，不是堆数字）

- **0 → 4**：完整 prompt 约 1000 token，1.5B 模型把「14:00—16:00」当成 `day` 过滤、把订单量写成 `SUM(weight_kg)`、写出 `hour_bucket = 6` 这类非法 SQL（24 题里只有 7 条 SQL 能执行）。聚焦 prompt 后 11 条可执行、4 条答对 → **长 prompt 遵循能力是部分原因，但不是全部**。
- **4 → 7**：把计算口径固化进工具，模型不必再生成 SQL。但此时只做类型校验，模型几乎对每题都填 `day=4`（"全部 5 天"被读成 day 编号）——**`day=4` 是合法值，schema 校验拦不住语义幻觉**。
- **7 → 22**：加一层确定性的**问句约束校验**：只从问题文本判断是否真的提到 day / `HH:MM—HH:MM` 时间窗 / 具体禁飞区，没提到就把对应可选参数丢弃；约束**不读 golden、不读正确工具**。这是上游「模型提议、本地代码按 schema 校验」边界的加强版，也是工具层固有的能力。
- **22 → 24**：剩下 2 例是 **C01 / C03 工具选错**（都应选 `drone_demand_aggregate`，被"禁飞区"带去 `no_fly_conflict_count`）。这与 §4 里 v1 规则式 resolver 的失效题**完全重合**——复合措辞「禁飞区活跃的窗口内有多少订单」无论规则还是 LLM 都会被主题名词带偏，v2 的「所求量」判定正是为此设计。规则式工具层因此仍能到 24/24。

### 这个补充实验回答了什么

主实验（§2）里两版数值正确率都是 24/24，因为 baseline 是「能写 SQL 的通用工具」。补上真实模型后，差别出现了：**当由模型来产出查询时，写 SQL 与选工具的数值正确率是 0% vs 91.7%**。差异来源不是玄学，而是三件可指认的事——计算口径固化、类型化参数、以及挡住合法但错误的参数幻觉。

### 局限（必须与结论一起讲）

1. **模型很小**：Qwen2.5-1.5B Q4、CPU 推理、长 prompt 遵循能力弱。**0/24 绝不能推广到 7B+ 或商用模型**；换强模型后 SQL 臂很可能大幅回升，阶梯会变平。
2. **不是纯模型能力对比**：工具臂带编排层（参数校验），SQL 臂没有。这正是"工具层"的定义，但也意味着这一对不是同等条件下的模型能力比较。
3. **约束校验来自规则**：它只解析问句里的 day / 时间窗 / 禁飞区关键词，不读答案；但它确实借用了 §4 的规则式解析思路。
4. **单次确定性运行**：`temperature=0 / seed=42` 下输出确定，重复不会改变结果，因此没有做多次采样，也**不报置信区间**。
5. **没有测强模型或 GPU**：结论严格限定为「该本地 1.5B CPU 模型条件下」。
6. `llm_sql_focused` 是**给 SQL 臂的有利条件**，用于排除长 prompt 解释；它不是主对比臂。

```bash
# 需要 E:/lowalt-llm/ 中的引擎与模型（见该目录 README.md）
python lowalt/eval/run_llm_eval.py --start-server --max-tokens 160 --timeout 240
```

## 8. 模型规模消融：工具层收益会不会随模型变强而消失？

§7 的 `0/24` 是在 1.5B 小模型上得到的，最大的质疑是「换个强模型就没这事了」。本节直接检验：同一 24 题、同一独立 SQL 答案键、同一 prompt、`temperature=0/seed=42`，只换本地模型权重。

| 模型 | LLM 自写 SQL | 聚焦 prompt SQL | **LLM 选工具** | 工具选择 | 答案完整性 | 平均耗时 |
|---|---|---|---|---|---|---|
| Qwen2.5-**1.5B** Q4_K_M | 0/24 (0%) | 4/24 (16.7%) | **22/24 (91.7%)** | 22/24 | 0.955 | 4.3 s |
| Qwen2.5-**3B** Q4_K_M | 2/24 (8.3%) | 5/24 (20.8%) | **23/24 (95.8%)** | 23/24 | 0.976 | 8.3 s |
| Qwen2.5-**7B** Q3_K_M | **5/24 (20.8%)** | 4/24 (16.7%) | **23/24 (95.8%)** | 23/24 | 0.948 | 17.1 s |
| 规则式工具层（无 LLM，§2） | — | — | **24/24 (100%)** | 24/24 | 0.990 | 0.005 s |

**答案**：阶梯**部分变平，但没有消失**。模型自写 SQL 随规模单调改善（0 → 2 → 5 题，0% → 8.3% → 20.8%），说明 §7 的 0/24 确实有一部分是模型能力问题；但工具臂始终稳定在 22–23/24，**绝对差距从 22 题缩到 18 题（91.7pp → 75pp），仍远未追平**。三档里工具臂在聚合类与空间类都是 8/8，残差集中在复合推理类（1.5B 6/8，3B/7B 7/8）——也就是 C01/C03 那两道被「禁飞区」带偏的工具选择题。

### 中途发现并修掉的一个编排层缺陷（方法论，值得单独讲）

7B **首跑**的工具臂只有 **10/24**，比 1.5B 的 22/24 还差，但工具选择是 23/24。诊断发现：prompt 里写了「不要编造时间窗」，更听话的 7B 于是把 `params` 整个留空（`{}`），工具退回默认全天，A02/S04/C02 等一批题答成了「全天值」。**这不是模型变笨，是编排层只做「删除非法参数」、不做「补全必要参数」**——模型越守规矩，反而越吃亏。

修法：`normalize_tool_params()` 现在同时 **prune**（丢掉幻觉的 day/zone/时间窗）和 **fill**（从问句文本抽取 day、`HH:MM—HH:MM` 时间窗、禁飞区并补进参数），仍然**不读 golden、不读正确工具**。因为 `temperature=0` 下输出确定，我用 `replay_params.py` **离线重放保存的原始模型输出**重新执行工具，没有重新推理、没有改动任何一个模型输出：

| | 重放前 | 重放后 |
|---|---|---|
| 1.5B 工具臂 | 22/24 | **22/24**（不变，说明修正无副作用） |
| 7B 工具臂 | 10/24 | **23/24** |

原始快照保留在 `llm_*_prereplay.json`。3B 是用修正后的脚本直接跑的，三档口径一致。

> 这一条本身就是可讲的工程结论：**编排层必须同时做剪枝与补全，否则「模型更听话」会被误读成「模型能力下降」**。

### 局限

1. **7B 用的是 Q3_K_M**（3.81 GB 单文件）：本机可用内存约 4.5 GB，Q4_K_M 是 4.68 GB 分卷，跑不动。量化更狠会损失能力，所以 7B 的 SQL 臂 5/24 **是偏保守的下界**；换 Q4 / 更大显存可能继续改善。
2. 三档都是 **1.5B–7B 的本地 CPU 小模型**，结论不能推广到 GPT/Claude 级强模型或经过 SQL 微调的模型。
3. 每题单次确定性运行，不报置信区间；三档共用同一套 prompt，prompt 本身未做规模适配。
4. 工具臂带编排层、SQL 臂没有（这是工具层的定义），所以这不是纯模型能力对比。
5. CPU 推理成本随规模线性上升（4.3 → 8.3 → 17.1 s/题），7B 全量耗时 22 分钟。

### 复现

```bash
python lowalt/eval/run_llm_eval.py --start-server --model E:/lowalt-llm/models/qwen2.5-3b-instruct-q4_k_m.gguf --tag 3b --max-tokens 160 --timeout 600
python lowalt/eval/run_llm_eval.py --start-server --model E:/lowalt-llm/models/qwen2.5-7b-instruct-q3_k_m.gguf --tag 7b --max-tokens 160 --timeout 600
python lowalt/eval/replay_params.py       # 编排层修正后的离线重放
python lowalt/eval/compare_models.py      # 生成 results/model_scaling.md
```

模型与引擎全部在 `E:/lowalt-llm/`（见该目录 README），无 API key、数据不出本机。
