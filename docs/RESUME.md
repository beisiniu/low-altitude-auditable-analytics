## 三、面试展开（如果被要求「讲讲这个项目」）

- **业务问题**：低空配送的运营分析里，「某时段需求峰值在哪个起降节点」「轨迹与禁飞区冲突几次」这类问题，用通用 BI/SQL 每次都要重写口径，数字散在临时查询里，无法追溯。
- **我的贡献边界**：没动模型层和核心框架。数据层（公开参数 → DuckDB 表）、工具层（3 个口径明确的函数）、评测层（24 题 + 独立答案键），外加验证器 2 行最小改动。
- **最硬的技术点**：上游规定「function 事实必须在 `RULES` 注册镜像重算规则，否则整个 job 失败」。我给 3 个新工具各注册一条规则，并把 Python 几何判定物化成 DuckDB 表，让只会 SQL 的验证器也能复核。
- **数据判断力**：发现该基准实例的禁飞区与配送网络几何零交集，冲突恒为 0——没有硬凑好看的提升，而是把它作为数据质量结论报告，另用明确标注的合成探针验证算法。
- **诚实的结论**：确定性主实验里数值正确率没有提升（通用 SQL 本来就能算对），提升在答案完整性和可复核性；**接上真实模型后**，差异才出现在正确率上。
- **第二轮迭代**：首轮评测暴露工具选择 19/24。根因是解析器匹配「话题名词」；改为识别「所求量」+ 显式 `AMBIGUOUS`/`UNRESOLVED` 三态，24/24 全 EXACT，8 条独立改写题 8/8，主评测三项指标不变。
- **第三轮（本地 LLM）**：四臂阶梯 0/24 → 4/24（聚焦 prompt 消融）→ 7/24（仅类型校验）→ 22/24（类型 + 问句约束校验）→ 24/24（规则式工具层）。每一级差值都有可指认的原因，见 `EVAL_REPORT.md` §7。
- **第四轮（模型规模消融）**：换 3B / 7B 复测，SQL 臂 0→2→5/24 单调改善但工具臂稳定 22–23/24，差距仍有 18 题。中途发现 7B 首跑只有 10/24 是**编排层只剪枝不补全**导致的（更听话的模型把参数留空），修复后离线重放到 23/24——这条本身就是很好的工程故事，见 §8。

## 四、3 分钟口头讲述稿（约 700 字，正常语速 2′50″–3′10″）

这个项目我想讲三件事：为什么这么改、数字怎么保证可信、以及我放弃了什么。

我用的是开源分析 Agent agentic-analytics，核心是「模型不碰算术」：数字全由 DuckDB 跑 SQL，报告发布前验证器逐条重算，对不上整份不发。数据取 IEEE DataPort 深圳前海 truck-drone 公开基准；主归档要登录，但页面有免登录的公开脚本，自包含 27 个真实坐标、两个时变禁飞区和订单参数。我用 AST 读常量、标准库确定性复现，day0 精确得到 52 单，与官方摘要一致。

**为什么只改数据层和工具层？** 这个框架有条硬规则：新增分析函数必须在验证器的 `RULES` 里注册一条镜像重算规则，查不到就判定引擎 bug、整个 job 失败。所以我加了需求聚合、禁飞区冲突、高度剖面三个工具，同时注册三条镜像规则；几何判定跑在 Python 里，我把它物化成 DuckDB 表，让只懂 SQL 的验证器仍能重新计数。这是我认为最值钱的设计。

**数字怎么可信？** 两层。验证器管一致性：每个数字都是 Fact，SQL 事实按参数重跑，函数事实从输入事实重算。正确性靠独立校验：我写了第二套点在多边形内的算法，用角度和而不是射线法，1681 个网格点判定完全一致，再加 12 个单测。必须说清楚——几何算法本身写错，验证器照样通过，一致性和正确性不能互相替代。

**trade-off 三个**：逐数字复核让聚合类耗时涨约 11 倍；几何用 Python 偏离了「计算全归 DuckDB」，我用物化表补回来；主评测为可复现完全没用模型，代价是证明不了有模型时工具层还有没有用——所以我补做了第二轮。

**第二轮**我在 E 盘放了一套本地 llama.cpp 加 1.5B 的 Qwen，不开云端点、不用 key，只监听 127.0.0.1，跑同一套 24 题：让模型自己写 SQL，0 题算对；只让它选工具、由工具算，22 题算对。中间做了消融——缩短 prompt，SQL 臂从 0 到 4 题，说明长 prompt 只是部分原因；只做类型校验时工具臂只有 7 题，因为模型几乎每题都幻觉出一个**合法**的 `day=4`，schema 校验挡不住语义幻觉；再加一层从问句出发的约束校验才到 22 题。剩下 2 题选错工具，恰好和规则式解析器最初失效的两题一模一样，都是「禁飞区活跃的窗口内有多少订单」这种被主题名词带偏的问法。为了检验是不是小模型的问题，我又换了 3B 和 7B：自己写 SQL 从 0 题涨到 5 题，确实在变强，但选工具稳定在 22 到 23 题，差距还有 18 题。中间还抓到一个坑——7B 首跑只有 10 题对，不是变笨，是它太听话把参数全留空，编排层补全后才回到 23 题。这是本地 7B 以下小模型的结论，不能推广到商用强模型。

最后主实验的数字我也诚实讲：两版数值正确率都是 24/24，我没设计天然算不对的 baseline 去刷提升；提升在答案完整性 0.399 到 0.990、可复核数字 24 到 242。数据集的禁飞区和配送网络几何零交集、冲突恒为 0，我把它当数据质量结论报告，另用标注清楚的合成探针验算法，没有藏起来。

> 若只剩 2 分钟：删去第 2 段数据来源细节、第 5 段的消融过程与三档复测，保留「0/24 → 22/24」「合法但错误的参数幻觉」和「换 7B 后差距仍有 18 题」三句即可。

## 五、大概率被追问的问题（提前准备）

| 追问 | 回答要点 |
|---|---|
| 「为什么提升不是正确率？」 | 确定性主实验故意让 baseline 能写 SQL，它本来就 100% 正确；拿没有空间能力的 baseline 比空间题，提升是被设计出来的。**接上真实模型后**差异才出现在正确率上（0/24 vs 22/24）。 |
| 「V2 通过率 100% 能说明算对了吗？」 | 不能。V2 只查一致性；几何正确性靠独立第二实现 + golden cases。这是本项目自己识别并补上的盲区。 |
| 「数据是真实的吗？」 | 坐标、禁飞区、订单过程参数来自公开基准（CC BY 4.0），轨迹是**明确标注的派生构造**，不是实测飞行；day0 复现 52 单与摘要吻合。见 `lowalt/data/SOURCES.md`。 |
| 「你说基于开源项目，改了几行？」 | `git diff` 可见：`recompute.ts` 改 2 处 + 新增 1 个规则文件，其余全在新目录 `lowalt/`。贡献边界清楚。 |
| 「上游跑通了吗？」 | Python 链路完整实测；本机 Bun 依赖下载失败，TS CLI 未跑通、补丁未经编译验证——如实说明，不隐瞒。 |
| 「零冲突那这个项目还有意义吗？」 | 有：这本身是数据质量结论；算法正确性用合成探针单独验证，报告里明确区分业务题与算法单测。 |
| 「修 5 例失效是不是过拟合？」 | 不是：先改判定对象（所求量而非话题名词），再用 8 条**不来自评测集**的改写题验证；24 题全 EXACT 且主结果三项指标不变。 |
| 「0/24 是不是你故意让模型输？」 | 不是：两个臂拿到**完全相同**的 schema 和口径定义；我还额外给 SQL 臂做了更有利的聚焦 prompt 消融，并逐条记录 SQL 错误都是模型自己写错口径或非法 SQL，不是解析失败。而且我**换 3B / 7B 复测过**，SQL 臂确实涨到 2/24、5/24——这一点我主动讲，不藏。 |
| 「换强模型后结论还成立吗？」 | 部分成立：SQL 臂 0→2→5/24 单调改善，阶梯确实在变平；但工具臂稳定 22–23/24，差距仍有 18 题（75pp）。7B 用的是 Q3_K_M（内存限制），是偏保守的下界；结论只覆盖本地 7B 以下小模型，不推广到商用强模型。 |
| 「7B 首跑怎么才 10/24，比 1.5B 还差？」 | 这是我最想讲的一个坑：不是模型变笨，是 prompt 里的「不要编造时间窗」被 7B 过度遵守，`params` 全留空、工具退回默认全天。说明**编排层只剪枝不补全**会让更听话的模型吃亏。改成同时剪枝+补全后，用保存的原始输出离线重放回到 23/24，模型输出一字未改。 |
| 「22/24 是不是靠规则开挂？」 | 约束校验只读问句文本（day / 时间窗 / 禁飞区），不读答案、不读正确工具；它本身就是工具层编排的一部分。同时保留了「仅类型校验」的 7/24 快照做消融，可以看到约束层的贡献。 |
| 「本地模型怎么跑的，要 key 吗？」 | 不需要任何 key：llama.cpp CPU 引擎 + Qwen2.5 1.5B/3B/7B GGUF 全在 E 盘，`llama-server` 只监听 127.0.0.1，数据不出本机。可用内存 ≥4 GB，且要加 `--no-repack`。 |
| 「下一步做什么？」 | ① 换 7B Q4 / 更大的模型或商用端点复测（当前 7B 受限于 Q3 量化与 CPU 内存）；② 构造模糊提问分布测 AMBIGUOUS 命中率；③ 把逐 fact 重算改增量，降 11× 耗时；④ 在 npm registry 可达环境完成 `bun run check` 验证 TS 补丁。 |
